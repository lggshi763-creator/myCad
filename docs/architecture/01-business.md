# §一 业务架构设计

> 回到导航：[../../ARCHITECTURE.md](../../ARCHITECTURE.md)

## 1.1 产品定位与核心价值主张

### 1.1.1 一句话定位

> **myCad 是一款"AI 原生"的开源参数化 CAD 内核与桌面应用，让单人也能完成原本需要团队协作的机械设计任务，并以"插件市场 + 云协同 + 私有化部署"构建可持续的商业生态。**

### 1.1.2 与现有产品的差异化矩阵

| 维度 | FreeCAD | Fusion 360 | SolidWorks | BricsCAD | **myCad（差异化）** |
|---|---|---|---|---|---|
| **许可** | LGPL，免费 | SaaS 订阅 | 商业永久+订阅 | 商业永久 | LGPL 内核 + 商业插件/云服务双层 |
| **架构** | 经典 OO + 拓扑命名问题 | 私有云端 | 私有 Parasolid | 类 AutoCAD 兼容 | DDD + 事件溯源 + ECS（结构化历史） |
| **AI 能力** | 无 | 有限（生成式设计） | 有限 | 弱 | **AI 原生**：约束生成、特征推荐、设计意图捕捉、协同编程 |
| **协同** | 无 | 云端但封闭 | PDM 集成 | 弱 | 基于事件流的开放协同协议（CRDT-friendly） |
| **扩展性** | Python 插件，C++ 模块 | API 受限 | 商业 SDK | LISP/Diesel/.NET | C++ 微内核插件 + Python 脚本 + WASM 沙箱（远期） |
| **交付方式** | 桌面 | SaaS 强绑定 | 桌面 | 桌面 | 桌面 + 自托管云 + 企业私有化 |
| **目标用户** | 业余 / 教学 | SMB / 教育 | 工业大客户 | AutoCAD 转移用户 | 个体设计师 / 小工坊 / 隐私敏感企业 |

**为什么这样定位**：
- **不与 SolidWorks 正面竞争**：工业大客户已被 PLM/PDM 深度绑定，迁移成本极高，单人开发者无法在功能广度上匹敌。
- **不与 Fusion 360 比 SaaS**：Autodesk 的云基础设施投入是天文数字，重复造轮子是必死路线。
- **找一个 FreeCAD 没解决的痛点**：FreeCAD 的"拓扑命名问题"与"无 AI"是结构性缺陷 — 前者源于其经典 OO 架构，后者源于社区资源限制。这两点恰好是 myCad 用 DDD+事件溯源 + AI 原生设计能根本性解决的。
- **私有化部署 = 切大厂奶酪不能切的蛋糕**：军工、医疗、国央企对设计数据出境零容忍，Fusion 360 / Onshape 的云端架构天然出局。这是个人开发者也能服务的高价值市场。

### 1.1.3 三阶段用户画像

#### 早期（0-1 年，0-100 用户）：**技术尝鲜者 + 开源贡献者**
- **典型画像**：30 岁机械工程师，业余玩 3D 打印 / RC 模型 / DIY 五金，受够 FreeCAD 的拓扑命名问题，会编程，听说"事件溯源 CAD" 来 GitHub Star
- **核心需求**：能跑通 "草图→拉伸→保存→重开" 完整闭环，架构清晰可读，欢迎 PR
- **成功指标**：100 GitHub Star，10 个 issue/discussion，3 个外部 PR
- **不要做什么**：不要在这阶段花时间做 GUI 美化、不要支持 STEP 互操作（除非贡献者主动来做）

#### 中期(1-3 年，1k-10k 用户）：**个体设计师 + 小工坊 + 教育市场**
- **典型画像 A**：独立家具设计师，不愿付 Fusion 360 年费，需要参数化 + 工程图 + DXF 导出
- **典型画像 B**：高校机械系教师，需要开源 CAD 用于教学，要求架构可作为案例讲解
- **典型画像 C**：3-5 人精密五金加工坊，需要 CAD→CAM 一体化但买不起 Mastercam
- **核心需求**：装配体、工程图、STEP/DXF 互操作、稳定性、中文文档
- **成功指标**：MAU 1000+，3 个商业插件上架，2 篇高校论文引用架构

#### 成熟期(3-5 年，10k+ 用户 + 企业客户）：**AI 原生设计 + 隐私敏感企业**
- **典型画像 A**：工业设计师工作室，使用 myCad 的 AI 功能（自然语言生成草图、智能特征推荐）将单项目工时压缩 40%
- **典型画像 B**：军工/医疗/国央企研发部门，采购 myCad 私有化部署 + 定制 AI 模型 + 年度技术支持
- **典型画像 C**：CAM/CAE 第三方厂商，基于 myCad 插件总线开发垂直行业方案
- **核心需求**：AI 能力深度（不是噱头）、企业级 SSO/审计/合规、长期支持承诺
- **成功指标**：3 家私有化部署企业客户，年商业收入 100 万级别，成为细分领域可被点名的选项

**为什么分三段而不是单一画像**：CAD 是典型的"长尾市场 + 高客单价企业"双层结构。早期技术驱动获取贡献者，中期社区驱动获取规模，后期商业驱动获取利润 — 三段策略不同、KPI 不同、做事不同。混同会导致早期就追求"GUI 漂亮"反而失去贡献者，或后期还在做"个人爱好者功能"而错失企业付费窗口。

### 1.2.3 个人开发者阶段的 MVP 定义

**MVP = "能完成一个真实的简单零件设计任务并保存复用"**

具体可验证场景（Phase 1 验收剧本）：
1. 用户启动 myCad，新建文档
2. 在 XY 平面创建草图，画一个矩形（含约束求解器自动求解）
3. 添加尺寸约束：宽 80mm、高 50mm
4. 退出草图，对该草图执行"拉伸"操作，参数 20mm
5. 旋转视图查看 3D 长方体
6. 保存为 `block.mycad`
7. 关闭程序，重新打开 `block.mycad`，参数树完整恢复
8. 修改草图宽度为 100mm，3D 模型自动联动更新
9. 撤销 / 重做正常工作（基于事件流）

**为什么这个 MVP**：
- **覆盖了所有架构核心路径**：UI → Command → DDD 聚合 → 事件 → EventStore → 几何重建 → ECS 更新 → 渲染。每个架构组件都被走过一遍。
- **可证伪**：上述 9 步任何一步崩溃，就说明架构有根本缺陷，必须立刻修复。
- **不包含装配/工程图**：因为它们的复杂度是单零件的 5-10 倍，纳入 MVP 会把开发周期拖到 18 个月以上，远超个人开发者的"信心保鲜期"。
- **包含 Undo/Redo**：因为这是事件溯源架构的核心卖点之一，不验证就是耍流氓。

**为什么不做什么**（MVP 阶段坚决砍掉）：
- 工具栏图标美化（functional ugly > pretty broken）
- 多语言（先确保中英文 UI 字符串能正常显示，i18n 框架预留即可）
- 主题切换（深色模式可以用系统调色板，不要花时间自做）
- 任何"用户偏好设置"页面（用配置文件即可）
- 网络功能（连"检查更新"都不要做）

## 1.3 商业模式设计

### 1.3.1 开源协议选型

#### 候选对比

| 协议 | 病毒性 | 商业插件可行性 | 私有化部署可行性 | 大厂"白嫖"防护 | 社区接受度 |
|---|---|---|---|---|---|
| **MIT/BSD** | 无 | ✅ 完全自由 | ✅ | ❌ 大厂可闭源衍生 | 高 |
| **LGPL v3** | 弱（仅修改内核需开源） | ✅ 动态链接调用 | ✅ | ⚠️ 部分防护 | 中高（CAD 圈认可，OCCT 用此） |
| **GPL v3** | 强（衍生作品全开源） | ❌ 商业插件几乎不可能 | ⚠️ 客户需开源其修改 | ✅ 强防护 | 中（商业用户回避） |
| **AGPL v3** | 极强（含网络服务） | ❌ | ❌（云客户需开源） | ✅ 最强防护 | 低（企业禁用） |
| **双协议**（内核 GPL + 商业版） | — | — | — | — | 高（典型如 Qt） |

#### 推荐方案：**LGPL v3 内核 + 商业插件 SDK 双层**

**为什么这样选**：
- **LGPL v3 与 OpenCASCADE 一致**：myCad 强依赖 OCCT，OCCT 是 LGPL v2.1。选 LGPL v3 是最自然的兼容选择，避免协议冲突的法律风险。
- **允许商业插件存在**：第三方可以开发闭源商业插件，通过动态链接调用 myCad API。这是构建"插件市场"商业生态的前提。
- **保护内核不被闭源 fork**：任何人修改 myCad 内核源码必须开源回馈，防止大厂直接拿走改名上线。
- **私有化部署友好**：企业客户部署 myCad 服务端不会触发协议传染（与 AGPL 关键区别）。
- **不选 GPL v3**：GPL 会扼杀商业插件生态，而插件生态正是商业模式核心。
- **不选 MIT**：MIT 太宽松，大厂可以拿去改名做闭源产品，单人开发者无法对抗这种"白嫖+换皮+营销碾压"组合拳。
- **不做双协议**：双协议商业版需要"贡献者协议（CLA）"，对早期个人项目是极大的法律和管理负担，会劝退社区贡献者。

**特殊例外**：
- AI 相关模块单独评估 — 训练好的模型权重不适用代码协议，应采用 Creative Commons 或自定义"商业使用需付费"协议
- 文档与示例：CC-BY 4.0
- 第三方贡献：要求提交 PR 时显式同意 LGPL v3（无 CLA，PR 行为本身即是同意）

### 1.3.2 盈利路径

#### 收入来源（按重要性排序）

**1. 私有化部署 + 企业支持合同（核心收入，60-70%）**
- **目标客户**：军工、医疗器械、国央企研发部门
- **产品形态**：myCad Enterprise = 内核 + 商业插件包（高级 AI、协同、审计、SSO/LDAP）+ 部署支持 + SLA
- **定价**：
  - 基础版：5 万元/年（≤20 用户，社区支持升级版）
  - 专业版：20 万元/年（≤100 用户，含远程支持 + AI 算力包）
  - 旗舰版：50-200 万元/年（无限用户 + 现场实施 + 定制开发）
- **为什么这是核心**：单笔大、续费高、护城河深（一旦部署就难替换）；个人开发者只需服务 5-10 家就能覆盖年度生活成本

**2. 插件市场分成（中期主力，20-30%）**
- **分成结构**：免费插件 0 抽成；付费插件 70/30（开发者拿 70%，平台拿 30%，对标 Steam）
- **平台职责**：
  - 提供统一支付（接入 Stripe / 支付宝）
  - 数字签名（防恶意插件）
  - 评分评论系统
  - 自动更新分发
- **为什么 30% 而不是 15% 或 50%**：15% 不够覆盖支付通道+服务器+签名审核成本；50% 会劝退开发者；30% 是 Steam/Apple 验证过的均衡点

**3. 云协同服务订阅（远期，可选）**
- **产品形态**：myCad Cloud — 基于事件流的多人实时协同 + 云存储 + 自动备份
- **定价**：
  - 个人版：免费 5GB
  - 团队版：50 元/用户/月，无限存储
  - 企业版：定制
- **为什么放远期**：云基础设施需要专人运维，个人开发者初期没有精力。等社区贡献者中出现愿意运营的合伙人再启动。

**4. 培训与认证（长尾，5-10%）**
- 官方认证课程（线上视频 + 考试）
- 企业内训（按天计费 5000-1 万元/天）
- "myCad 认证开发者"徽章

**为什么不做"全功能闭源版收费"**：这种"开源版残废 + 闭源版完整"模式（Foxit、UltraEdit）在 CAD 领域已被 SolidWorks/Onshape 占据，单人开发者无法竞争。且会撕裂社区信任。

### 1.3.3 0 → 100 → 1k → 10k 用户冷启动路径

#### Phase A：0 → 100（前 6 个月，靠技术内容）
- **核心动作**：写技术博客 / 知乎 / B 站视频，主题如：
  - "为什么我决定从零写一个 CAD 内核"
  - "用 DDD + 事件溯源解决 FreeCAD 的拓扑命名问题"
  - "C++20 现代特性在 CAD 内核中的实战"
  - "OpenCASCADE 入门到精通：我踩过的 50 个坑"
- **目标渠道**：知乎、CSDN、B 站、HackerNews、r/cpp、r/CAD
- **关键节点**：在 GitHub 仓库 README 顶端放一个 GIF 演示（拉伸 + 草图修改联动），10 秒内说服访客点 Star
- **里程碑标志**：一篇博客被 100+ 人转发，issues 出现外部用户

#### Phase B：100 → 1k（6-18 个月，靠 MVP 落地）
- **核心动作**：完成 Phase 1 MVP 并发布 v0.1
- **传播策略**：
  - 制作 "myCad vs FreeCAD：5 个架构差异" 对比视频
  - 在 FreeCAD 论坛、3D 打印社区、机械设计 QQ 群里"克制地"分享（不要硬广，提供真实价值）
  - 联系国内 5-10 个 3D 打印 / 机械教育 KOL 寄"早期用户体验邀请"
- **关键节点**：第一个外部用户做出可运行的 STL 模型并发到社交媒体
- **里程碑标志**：日活 50+，外部 PR > 5 个

#### Phase C：1k → 10k（18-36 个月，靠生态裂变）
- **核心动作**：上线插件市场，推动第三方开发者
- **冷启动插件市场**：
  - 自己先开发 3-5 个高质量免费插件（DXF 高级导出、参数化齿轮库、3D 打印切片预览）
  - 举办"插件开发大赛"，奖金 5000-2 万元
  - 与 1-2 家 CAM 公司合作，让其插件首发 myCad
- **里程碑标志**：第三方插件 > 30 个，付费插件 > 5 个，月 GMV > 1 万元

### 1.3.4 AI 商业化引入时机

| 时间窗 | 状态 | AI 能力 | 商业策略 |
|---|---|---|---|
| Phase 0-1（0-12 月） | 内核构建 | **不做 AI**，预留 AI Port 接口 | 不开发，不宣传 |
| Phase 2（12-24 月） | MVP 已交付 | 上线"自然语言→草图"基础功能 | 内置免费版 + 高级版（订阅 50 元/月或买断 999 元） |
| Phase 3（24+ 月） | 生态成型 | 设计意图理解、装配自动约束、智能诊断 | 企业版独占 + 开放 LLM Adapter 让企业接入私有模型 |

**为什么不能更早**：
- AI 功能依赖底层数据结构稳定（事件流、约束图、ECS 状态）。底层频繁重构会让 AI 功能持续被破坏，最终烂尾。
- AI 能力需要"对比基线"。没有 MVP 就没有"AI 让效率提升 40%"的可量化卖点。
- 个人开发者的 AI 工程经验有限，过早进入会拖累内核开发节奏。

**为什么不能更晚**：
- 行业 AI 化窗口可能 2026-2028 年迎来爆发，错过这一窗口将失去差异化定位。
- AI 是 myCad 区别于 FreeCAD 的核心叙事，最迟 Phase 2 必须有可演示的 AI 能力，否则"AI 原生"沦为空话。

## 1.4 竞争与生态战略

### 1.4.1 插件开发者生态建设路径

#### SDK 设计三大原则

1. **API 稳定性高于功能丰富性**
   - 公共 API 一旦发布，2 年内不允许破坏性变更（Deprecate→Warn→Remove 走 4 个版本）
   - 内部 API 与公共 API 严格分离（用 `_internal` 命名空间隔离）
   - **为什么**：插件开发者最痛恨"升级即崩溃"，这是 Sketchup Ruby API 长期被吐槽的核心原因

2. **错误信息高于文档完备性**
   - SDK 使用错误必须返回结构化诊断（错误码 + 上下文 + 修复建议链接）
   - 用 `std::expected` 替代异常，强制开发者处理错误路径
   - **为什么**：好的错误信息抵得上 100 页文档，且开发者更可能读到

3. **Hello-World 必须 5 分钟内跑通**
   - SDK 仓库根目录有 `examples/hello_plugin/`，CMake 一键构建
   - **Visual Studio 一键调试配置**（详见 [§八 vs-toolchain §8.8](./08-vs-toolchain.md)）
   - **为什么**：5 分钟是开发者评估新平台的耐心上限，超过就流失

#### 文档策略

| 文档类型 | 目标读者 | 工具 | 优先级 |
|---|---|---|---|
| **API Reference** | 已上手的开发者 | Doxygen 自动生成 | P0 |
| **Tutorial**（手把手教程） | 第一次接触的开发者 | 手写 Markdown + 代码示例 | P0 |
| **Architecture Guide**（架构理解） | 想做深度集成的开发者 | 手写 + 架构图 | P1 |
| **Cookbook**（常见问题方案） | 卡在某个具体问题的开发者 | 社区 wiki | P1 |
| **Video Tutorial** | 视频学习偏好者 | B 站频道 | P2 |

**为什么这个排序**：Tutorial > Reference 是反直觉的 — 大多数项目认为"先有 API 文档，再有教程"，但实际上没有教程的 API 文档是开发者无法切入的，只会被竞争对手推荐替代。

#### 社区运营节奏

- **每周**：GitHub issue triage（标签分类、回复、引导贡献）
- **每两周**：Discord/微信群"Office Hour"（开发者答疑 1 小时）
- **每月**：发布日志博文 + 社区贡献者鸣谢
- **每季度**：路线图公开更新 + 社区投票决定 P1 优先级
- **每年**：myCad 社区大会（线上为主，1 天，邀请贡献者分享）

**为什么强调节奏可预测性**：开源社区最忌讳"维护者突然消失"。固定节奏让贡献者建立信任，即使你某次更新内容平淡，"按时出现"本身就在传递"项目活着"的信号。

### 1.4.2 OpenCASCADE 上游协作策略

OCCT 是 myCad 的核心依赖，与上游的关系决定项目可持续性。

#### 协作三阶段

**Stage 1：纯使用者（0-12 月）**
- 不向 OCCT 提交 PR（你的工作量已经爆表）
- 但严格遵守 LGPL v2.1 协议，所有 OCCT 修改都通过 myCad 的 Adapter 层封装而非直接 patch OCCT 源码
- 在 myCad 文档中清晰标注 "Powered by OpenCASCADE"
- **目标**：合规 + 不被 OCCT 维护者反感

**Stage 2：偶尔贡献（12-24 月）**
- 当你发现 OCCT 的 bug 时，提交修复 PR（哪怕只是文档错字）
- 在 OCCT 论坛参与讨论，建立技术信用
- **目标**：在 OCCT 社区建立你的开发者身份，未来反向影响 API 设计

**Stage 3：深度合作（24+ 月）**
- 推动 OCCT 接受对 myCad 关键的 API 改进
- 探索是否可以基于 OCCT 之上发起一个"现代 C++ CAD 内核"工作组
- **目标**：从"使用者"升级为"生态共建者"

#### 风险点与对策

| 风险 | 对策 |
|---|---|
| OCCT 大版本升级破坏 myCad | Adapter 层 + 锁定特定 OCCT 版本，每次升级走完整回归测试 |
| OCCT 项目长期不更新 | 监控 OCCT 提交频率，必要时考虑 fork 维护（最坏情况）；详见 [§九 self-host-strategy §9.2.1](./09-self-host-strategy.md) |
| OCCT 商业版（Open CASCADE Technology Pro）切走核心功能 | 关键算法（如布尔运算）准备 Plan B：探索 CGAL 或自研的可能性 |

### 1.4.3 CAD 算法专利雷区与规避

CAD 行业是专利密集区，个人开发者必须主动识别雷区。

#### 高风险专利领域（已知存在大量专利）

1. **拓扑命名（Topological Naming）**
   - **持有方**：PTC（Pro/E 起源）
   - **风险点**：自动生成稳定的特征引用 ID 的某些方法
   - **规避**：myCad 采用基于事件溯源的"事件 ID + 派生路径"方案，与传统拓扑命名机制有本质差异（结构上来源于 Git 模型，非 PTC 模型），降低侵权风险
   - **行动**：纳入 ADR 文档，明确说明设计来源以备未来抗辩

2. **参数化历史树（Feature History Tree）**
   - **持有方**：Dassault（SolidWorks）、Autodesk
   - **风险点**：基本概念已是公知，但特定 UI 交互模式可能被覆盖
   - **规避**：不复制竞品的 UI 交互细节（如双击编辑、拖拽重排序的特定动画），用自己的设计

3. **直接建模（Direct Modeling，与参数化对立）**
   - **持有方**：Siemens（Synchronous Technology）
   - **风险点**：如果 myCad 引入"直接编辑面/边而保留参数关系"功能要小心
   - **规避**：远期再考虑，引入前做专利清查

4. **约束求解器算法**
   - **持有方**：D-Cubed（被 Siemens 收购）持有大量约束求解专利
   - **风险点**：某些特定的约束分解策略
   - **规避**：使用 SolveSpace 求解器（已被广泛验证为可商业使用）或自实现基于公开论文（如 Hoffmann 的几何约束论文）的方案

5. **B-Rep 数据结构与布尔运算**
   - **现状**：核心算法基本是 1990 年前的工作，专利大多已过期或公知
   - **规避**：通过使用 OCCT 的 B-Rep 实现，将专利风险转嫁给上游

#### 主动防御措施

- **建立 ADR 文档库**：每个重要设计决策记录"灵感来源 / 公开论文引用"，证明独立设计
- **避免阅读竞品反编译代码**：清白来源原则
- **不直接 fork 商业 CAD 代码**：哪怕是泄露的源码也不能看
- **专利防御性公开**：myCad 的创新设计（如基于事件溯源的 CAD 历史）通过博客 / 论文公开发表，建立"现有技术（Prior Art）"，防止他人反过来申请专利再起诉你
- **早期不主动专利申请**：申请专利成本高，对个人开发者不划算；进入企业客户阶段（年收入 100 万+）后再考虑申请 1-2 个核心专利防御

#### 法律风险量级评估

| 阶段 | 实际诉讼风险 | 应对预算 |
|---|---|---|
| Phase 0-1（用户 < 1k） | 极低（大厂不会理你） | 0，专注开发 |
| Phase 2（用户 1k-10k） | 低 | 准备 1-2 万元法律咨询费用 |
| Phase 3（企业客户阶段） | 中 | 法律顾问年度顾问 5-10 万元，准备应诉预算 |

**为什么这样判断**：CAD 大厂的法律部门只在你"实际威胁到他们的市场"时才会出手。Phase 0-2 的开源项目对他们而言就像 LibreOffice 之于微软 — 不值得花律师费。但进入企业市场后，你抢的就是 SolidWorks/Inventor 的真金白银，必须做好法律准备。
