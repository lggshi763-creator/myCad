# §七 风险识别与缓解策略

> 回到导航：[../../ARCHITECTURE.md](../../ARCHITECTURE.md)

## 评分标准

**概率（Probability）**：
- 🟢 低（< 20%）— 可能但不预期
- 🟡 中（20%-60%）— 大概率会遇到
- 🔴 高（> 60%）— 几乎一定会遇到

**影响（Impact）**：
- 🟢 低 — 延迟数周或局部返工
- 🟡 中 — 延迟数月或重大重构
- 🔴 高 — 项目阻塞、商业模式失败、放弃风险

## 7.1 风险一：个人开发者资源瓶颈（时间 / 精力 / 资金）

**概率**: 🔴 高（**几乎一定会遇到**）
**影响**: 🔴 高（**最可能导致项目失败的根因**）

### 风险描述

CAD 是工程量大、复杂度高的产品。SolidWorks 用了 30 人 5 年到 1.0，FreeCAD 是数十人的开源接力。你一个人 + AI 工具去做，资源约束会从 Day 1 持续存在：

- **时间**：本职工作之外，每天 2-3 小时实际编码时间，周末也只能挤出 8-10 小时 → 周均 25-35 小时
- **精力**：CAD 涉及几何/数值/UI/架构/算法多个深水区，单人难以同时保持所有领域的高度专注
- **资金**：开源前期零收入，但需要支付：vcpkg 私有 registry、苹果开发者账号（$99/年）、可能的 SaaS 服务（CI 大型 runner、AI API、对象存储）、域名 + 服务器

### 早期信号（一旦出现立刻警觉）

- 连续 2 周以上没有 commit
- Sprint 估时频繁 2x 超出
- 开始把 P1 任务降级为 P2 自我安慰
- 周末"只想休息"超过 3 个连续周末
- 开始嫉妒"如果有团队多好"的念头持续出现
- 健康指标恶化（睡眠、运动、社交都受影响）

### 缓解措施（按重要性排序）

#### M1.1 严格时间盒（Time Boxing）
- **每日**：固定 2 小时编码时间窗（如晚上 21:00-23:00），其他时间不工作
- **每周**：明确 1 天为"零编码日"（如周三或周日），用于充电、读书、运动
- **每 8 周**：1 周完全休息（不开仓库），称为"安息周"
- **为什么**：CAD 是 5+ 年的马拉松，不是 6 个月冲刺。烧光自己 = 项目死。

#### M1.2 固定的功能 vs 弹性的进度
- **固定**：按 Phase 0 → Phase 1 → Phase 2 → Phase 3 顺序执行，不跳跃
- **弹性**：Phase 1 是 6-9 个月还是 12 个月，取决于实际进度，**不为了赶时间砍质量**
- **为什么**：开源项目的"按时发布"对个人项目意义有限；"质量稳定"比"按时"重要 10 倍

#### M1.3 资金预算上限
- **第一年**：设定 1 万元年度预算上限（域名 + 服务器 + 工具订阅）
- **第二年**：根据是否有商业进展决定是否提升到 3-5 万元
- **第三年起**：商业收入足以覆盖成本前不超过 5 万元/年
- **永远不**：从信用卡/借贷投入开发
- **为什么**：钱压力 → 焦虑 → 决策扭曲 → 砍质量 → 失败

#### M1.4 AI 工具最大化使用
- 把 [§三 AI 工作流](./03-ai-workflow.md) 的 Claude + DeepSeek 工作流落实到位
- 任何"做了 1 小时仍卡住"的任务，立刻换 AI 重做
- 单次写超过 200 行新代码 = 应该让 DeepSeek 写
- **为什么**：AI 是个人开发者唯一能用上的"虚拟团队"，必须用足

#### M1.5 早期建立可验证里程碑
- Phase 0 末必须有"可邀请朋友体验的 alpha"
- Phase 1 末必须有"可在社区发布的 v0.1"
- 这些里程碑是给自己的"信心保鲜剂"，避免 1 年看不到成果而崩盘

#### M1.6 心理健康基础设施
- 找 1-2 个开源圈朋友定期聊（不必是 myCad 贡献者，能理解你的处境即可）
- 维护 dev log（即使简短，记录"今天做了什么 / 卡在哪"），作为情绪出口
- 警觉性焦虑或抑郁信号，及时寻求专业帮助

#### M1.7 商业化时机的纪律
- 不要因为缺钱就过早商业化（破坏开源信任）
- Phase 2 末才上线高级版功能，Phase 3 才考虑企业版
- 企业版谈判前必须有 v1.0 + 至少 2 个免费试用客户案例

### 失败回退方案

如果 Phase 1 末（约 12 个月）仍未达到 v0.1 可发布状态：
- **不要拖**：诚实地宣布"重新校准"，写一篇 retrospective 公开
- **简化范围**：把 v0.1 的"必备功能"砍到 50% — 保留草图 + 拉伸即可，砍掉装配/工程图
- **接受现实**：CAD 真的难，自己一个人 +/-50% 的估时偏差完全正常
- **不要放弃**：至少完成 Phase 0 的"基础设施 + 架构 ADR" 已经是有价值的开源贡献

## 7.2 风险二：OpenCASCADE LGPL 对商业化的影响

**概率**: 🟡 中（**取决于商业模式细节执行**）
**影响**: 🟡 中（**主要影响商业插件与企业版**）

### 风险描述

OCCT 采用 LGPL v2.1 协议，核心约束：
- 任何对 OCCT 源码的修改必须开源回馈
- 静态链接 OCCT 的应用必须以兼容协议（通常 LGPL）发布
- 动态链接 OCCT 的应用可以是商业闭源

具体到 myCad 商业模式可能受影响的场景：

| 商业场景 | LGPL 影响 |
|---|---|
| **myCad 内核（LGPL）+ 闭源商业插件（动态加载 myCad）** | ✅ 合规 |
| **myCad 高级版功能（同进程闭源代码）** | ⚠️ 高级版必须 LGPL（破坏闭源诉求） |
| **企业私有化部署（不分发 = 不触发 LGPL）** | ✅ 合规 |
| **Cloud SaaS 部署（同样不分发）** | ✅ 合规 |
| **基于 myCad 的闭源衍生产品** | ❌ 不可能（myCad 自身 LGPL） |

### 早期信号

- 第一个商业插件作者询问"我可以闭源吗" → 触发法律解释需求
- 企业客户询问"如果我们魔改 myCad 内核可以保密吗" → LGPL 不允许
- 律师审查时发现某个 OCCT 模块用了不同协议（OCCT 商业版 vs 社区版）

### 缓解措施

#### M2.1 严格 LGPL 隔离设计
- **myCad 内核 → 永远不使用 OCCT 的"模块化加载"机制把内核与 OCCT 静态链接**
- **vcpkg 配置**：OCCT 编译为 shared library（动态库），由 myCad 通过 dlopen 加载或 link 时引用
- **为什么**：动态链接是 LGPL 合规的关键防火墙

#### M2.2 商业插件的 SDK 设计
- SDK 只暴露 myCad 自有的 API（IPlugin、IPluginHost、IGeometryPort）
- **绝不**让插件直接 #include 任何 OCCT 头
- 插件作者无需碰 OCCT 即可完成绝大多数功能 → 插件可以闭源
- **为什么**：把 OCCT 的"传染性"圈在 myCad 自己的边界内

#### M2.3 高级版功能的策略
- **不**做"同进程闭源高级功能"模式
- **改用**：高级版 = "插件包 + 云服务订阅"
  - 高级 AI 功能在云端运行，本地只是 API 客户端
  - 高级 UI 功能作为闭源插件分发（通过 SDK 调用 myCad，不静态链接 OCCT）
- **为什么**：把价值放到"云端 + 插件"层，绕开 LGPL 约束

#### M2.4 企业版的私有化策略
- 企业部署 = 不分发到第三方 = 不触发 LGPL
- 客户内部修改 myCad 内核也无需开源（仅"自用"）
- 但要在合同中明确：客户**不能**对外分发其修改版本
- **为什么**：LGPL 的"修改必须开源"仅在分发时触发

#### M2.5 法律咨询基线
- Phase 0：自己读完 LGPL v2.1 全文 + GPL FAQ
- Phase 1：第一次商业接触前，找 1 次专业法律咨询（5000-1 万元）
- Phase 2 起：保留法律顾问年度服务（5-10 万元/年）
- **为什么**：开源协议法律细节难，自学只能保底，关键节点必须专业意见

#### M2.6 备选方案：OCCT 商业版评估
- OCCT 公司提供商业版（"Open CASCADE Technology Pro"），不带 LGPL 约束
- 价格：议价制，估计年度数十万人民币
- **何时考虑**：年商业收入 100 万+ 后，如果 LGPL 真的成为商业瓶颈
- **当前不考虑**：成本远超预算，且开源版功能足够

### 失败回退方案

如果某天发现某个核心商业模式被 LGPL 阻断：
- **不要慌**：90% 的"LGPL 阻断"问题其实是误读，先咨询律师
- **真有问题**：调整商业模式而非协议（动态链接重构、改云服务）
- **极端情况**：探索 OCCT 商业版 OR 长期投入研发独立几何内核（远期项目，详见 [§九 §9.2.1](./09-self-host-strategy.md)）

## 7.3 风险三：约束求解器实现难度超出预期

**概率**: 🟡 中（**集成 PlaneGCS 顺利则避免；自实现则高风险**）
**影响**: 🔴 高（**草图功能不可用 = MVP 失败**）

### 风险描述

约束求解器是 CAD 中难度最高、坑最多的子系统：
- 数值优化收敛性问题（病态雅可比、奇异点、局部最优）
- 几何约束的非线性强（切线、距离、角度方程）
- 性能要求高（拖拽时 60 fps 增量求解）
- 用户体验差异巨大（求解失败时如何反馈）

历史教训：FreeCAD 的 Sketcher 经过 10+ 年才稳定。SolveSpace 是单人 5 年作品但是 GPL 协议不可用。自实现风险极高。

### 早期信号

- 第一次 PlaneGCS 集成在某个测试用例上结果不正确
- 性能 benchmark 显示 50 变量求解就超过 200ms
- 用户报告"添加约束后图形跳到完全不合理的位置"
- 增量求解结果与完整求解结果不一致

### 缓解措施

#### M3.1 优先集成 PlaneGCS（不自实现）
- Phase 1 Sprint 1.A2 全力投入 PlaneGCS 集成
- 即使遇到困难也不切到自实现
- **为什么**：PlaneGCS 已被 FreeCAD 验证 10 年，避免 90% 的求解器陷阱

#### M3.2 PlaneGCS 集成的具体策略
- **方式 1（首选）**：从 FreeCAD 仓库直接提取 src/Mod/Sketcher/App/planegcs/ 目录，作为独立子模块
- **方式 2**：等待社区是否有人发布独立的 planegcs vcpkg port
- **方式 3**：自己提交 vcpkg port（这个工作单独估时 1-2 周）
- 接口隔离：PlaneGCS 类型不出 PlaneGcsSolver Adapter 边界

#### M3.3 早期建立测试基准
- Phase 1 Sprint 1.A2 第一周即建立"求解器测试基准集"：
  - 50 个典型草图场景（来自真实 CAD 教学案例）
  - 每个场景的预期解 + 容差
  - benchmark 性能指标
- 后续任何求解器改动必须跑过基准集
- **为什么**：求解器是"差之毫厘谬以千里"的子系统，没有基准等于盲飞

#### M3.4 用户反馈的兜底设计
- 求解失败时**绝不**让草图进入不可恢复状态
- 失败 → 回退到求解前状态 + 弹出诊断
- 诊断必须是人话（"约束 #5 与约束 #8 冲突，建议删除其一"）而非数学（"Jacobian singular"）
- **为什么**：CAD 用户对求解器失败容忍度极低，用户体验是关键

#### M3.5 增量求解的渐进引入
- v0.1 仅支持完整求解（每次调用从初始猜值开始）
- v0.2 引入增量求解（拖拽场景）
- 不要在 v0.1 同时做两种 → 复杂度叠加难定位 bug
- **为什么**：增量求解对正确性要求更高，需要稳定的完整求解作为对照基准

#### M3.6 自实现备选方案的预先调研
- Phase 0 阶段就阅读：
  - Hoffmann 的几何约束论文
  - SolveSpace 的源码注释（不能直接用代码，但思路可参考）
  - Eigen 的 LM 求解器文档
- **不写代码**，只做笔记 + ADR 草稿
- **为什么**：万一 PlaneGCS 集成失败，至少不是从零开始研究。详见 [§九 §9.2.4](./09-self-host-strategy.md)

### 失败回退方案

如果 Phase 1 中后期 PlaneGCS 路线彻底失败：
- **第一步**：诚实评估失败原因（许可？技术？时间？）
- **第二步**：v0.1 砍掉"约束求解"功能，仅做"自由绘图 + 尺寸标注（不求解）" — 仍然是可用的，类似简化版 AutoCAD
- **第三步**：Phase 2 再启动自实现 Eigen LM 路线，作为 1.x 版本的核心改进
- **不要**：在 Phase 1 强行自实现拖累整个 MVP

## 7.4 风险四：AI 工具上下文窗口限制导致架构漂移

**概率**: 🔴 高（**确定会发生，关键是控制程度**）
**影响**: 🟡 中（**短期质量下降，长期可累积成技术债**）

### 风险描述

DeepSeek 上下文窗口装不下整个项目代码库 → 实现时只能看到当前任务的局部 → 容易做出"局部合理但全局违反架构"的决策：

- 在 Domain 层 #include 了 OCCT 头（DeepSeek 不知道这是禁忌）
- 复制了已有工具函数的逻辑（DeepSeek 没看到既有实现）
- 命名风格漂移（用了 snake_case 而非 camelCase）
- 错误处理用 throw 而非 std::expected
- 创建了与现有类功能重叠的新类

随时间累积 → 代码库出现"AI 风格混乱地块"，最终需要大手笔重构。

### 早期信号

- Claude Code 审查 PR 频繁标出"硬约束违反"
- 同样的功能在不同模块出现两次以上实现
- 命名风格一致性下降（grep 同一概念出现多种写法）
- 测试虽然过但"代码看着不对劲"
- 你自己回头看代码已经看不懂为什么这么写

### 缓解措施

#### M4.1 强化 §3.2 CONTEXT.md 规范的执行
- 每个交给 DeepSeek 的任务**必须**有专属 CONTEXT.md
- CONTEXT.md 必须列出该任务相关的"既有实现"（避免重复造轮子）
- CONTEXT.md 必须列出"硬约束"清单
- **为什么**：CONTEXT.md 是阻挡漂移的第一道防线，省略 = 必崩

#### M4.2 强化 §3.6.3 架构合规审查的执行
- DeepSeek 提的每个 PR 必须经过 Claude 架构合规审查
- 审查不通过即返工，绝不"先合并以后再说"
- 每周累积一次"违规模式"分析（发现常犯的 3-5 个错误）→ 反向更新 CONTEXT.md 模板
- **为什么**：审查是第二道防线，比第一道更重要

#### M4.3 自动化工具拦截
- **clang-tidy 配置**：用 misc-include-cleaner、cppcoreguidelines-* 等规则拦截常见违规（Visual Studio 内置 clang-tidy 自动应用）
- **自定义 lint**：写脚本检测"Domain 层是否 #include OCCT/Qt/OpenGL"
- **CI 阻断**：lint 不过 = PR 不能合并
- **为什么**：自动化是第三道防线，比人工审查更稳定

#### M4.4 定期架构体检
- 每月一次"架构健康度审查"（Claude 主导）
- 检查项：
  - 各层依赖是否仍然单向
  - 接口是否被绕过
  - 命名一致性
  - 测试覆盖率趋势
- 输出健康度报告 → 写入 docs/architecture-audits/YYYY-MM.md
- **为什么**：第四道防线，捕捉慢性漂移

#### M4.5 重构留白
- 每个 Phase 留出 10-15% 时间作为"技术债偿还"
- 专门用于重构发现的漂移问题
- 不要等到积累成大问题
- **为什么**：温和重构成本远低于大手术

#### M4.6 架构图与文档保持同步
- 任何接口变更必须同步更新 [docs/architecture/](./)
- 任何新增 ADR 必须在 [ARCHITECTURE.md](../../ARCHITECTURE.md) 引用
- 让 Claude Code 在每次架构性 PR 中**主动检查**文档同步
- **为什么**：文档过期 → 后续 AI 用过期文档 → 漂移加速

### 失败回退方案

如果 Phase 1 末发现严重架构漂移（10%+ 代码违反硬约束）：
- **专题重构 sprint**：用 1-2 周专门处理（不混合功能开发）
- **优先级**：先修硬约束违反 → 再修接口绕过 → 再修命名 → 最后处理测试覆盖
- **避免**：不要试图"一次性全修复"，按文件逐个清理

## 7.5 风险五：开源生态冷启动失败

**概率**: 🟡 中（**60% 的开源项目长期无外部贡献者**）
**影响**: 🔴 高（**无生态 = 无插件市场 = 商业模式核心崩塌**）

### 风险描述

商业模式高度依赖开源生态：
- 插件市场 30% 分成 → 需要第三方开发者
- 社区贡献 → 减轻个人开发者负担
- 用户口碑 → 商业获客的主要来源

开源生态冷启动失败的常见原因：
- 项目长期单兵作战，外部贡献者认为"作者一个人玩"
- 文档不足，新人无法上手
- Issue 响应慢，贡献者失去耐心
- 架构过于个性化，新人理解成本高
- 没有"小贡献"入口（issues 全是大块功能）

### 早期信号

- v0.1 发布 1 个月后 GitHub Star < 50
- v0.1 发布 3 个月后无外部 PR
- 自己发了博客但转发数 < 10
- 加入的 CAD 社区无人响应
- discussions 区 issue 区都是死寂

### 缓解措施

#### M5.1 内容驱动的曝光（Phase 0 起就做）
- 每月 1 篇深度技术博客（中英双版）
- 主题方向：架构决策、踩坑经验、CAD 内部原理科普
- 发布渠道：知乎、掘金、CSDN、Reddit r/cpp、HackerNews、Lobste.rs
- **目标**：v0.1 发布前累积至少 6 篇高质量博客 → 自带流量

#### M5.2 GIF / 视频优先于文字
- README 顶端放 10-30 秒功能 GIF
- 关键功能录制 1-3 分钟 YouTube/B 站视频
- 每个 release blog 配 GIF
- **为什么**：开发者刷 GitHub 决策时间 < 30 秒，视觉吸引最高效

#### M5.3 "新人友好"基础设施
- `good first issue` 标签维护至少 5 个活跃 issue
- 每个 good first issue 必须包含：
  - 问题描述
  - 涉及的文件路径
  - 预期改动方向
  - 评估难度 + 估时
- CONTRIBUTING.md 写明：从 fork 到 PR 合并的具体步骤
- **为什么**：把新人门槛从"看天赋"降到"有动机就能贡献"

#### M5.4 主动建立合作关系
- Phase 1 末识别 5-10 个相关项目（FreeCAD、PrusaSlicer、CAMotics 等）的活跃贡献者
- 主动到他们的 issue 区提供帮助
- 不要立刻"邀请加入 myCad"
- 6-12 个月后他们对你有印象时，再分享 myCad
- **为什么**：开源圈是关系驱动的，先付出再期望

#### M5.5 高频 + 可预测的发布节奏
- v0.1 起，每月一个 minor release（含 patch + 小功能）
- 每季度一个较大 release（含主题功能）
- Release notes 必须真诚（什么修了、什么没修、下一步什么）
- **为什么**：节奏感是社区信任的基础，"项目还活着"的最强信号

#### M5.6 透明的路线图与决策
- 公开 ROADMAP.md（基于 [§六 路线图](./06-roadmap.md) 简化版本）
- 每个 ADR 公开发布
- 重大决策走 GitHub Discussions RFC 流程
- **为什么**：透明度让贡献者感觉"我也是被尊重的一员"

#### M5.7 不要做的事
- ❌ 不要"鼓吹技术 vs FreeCAD 多牛" → 树敌于成熟社区
- ❌ 不要把所有时间花在"营销" → 没产品的营销 = 噪音
- ❌ 不要拒绝小贡献（"这个 PR 太小不接受"） → 一次拒绝 = 永久失去贡献者
- ❌ 不要在 Issue 区与用户对喷 → 即便对方明显错误

### 失败回退方案

如果 v0.1 发布 6 个月后仍然冷清：
- **诊断**：是产品问题（功能太少 / 难用）还是传播问题（曝光不够）
- **如果产品**：暂停新功能开发，专注稳定性 + 文档 + 教程
- **如果传播**：调整内容策略（视频化、社交媒体、直播开发）
- **极端情况**：接受"小众但活跃"的定位（类似 SolveSpace），调低商业预期，作为长期作品维护

## 7.6 风险六：大厂推出同类免费产品的竞争威胁

**概率**: 🟢 低（**短期低，长期中**）
**影响**: 🟡 中（**取决于 myCad 阶段与差异化程度**）

### 风险描述

竞争威胁的来源：
- **Autodesk** 推出 Fusion 360 的"个人完全免费版"（已发生，但有限制）
- **Onshape** 类似云端 CAD 进入个人市场
- **国内大厂**（华为、字节、阿里）切入工业软件
- **开源新势力**：某个有大公司背景的开源 CAD 项目突然崛起
- **AI 大厂**：OpenAI/Anthropic 发布"AI CAD"颠覆性产品

### 概率分阶段评估

| 时间窗 | 大厂动作可能性 | 原因 |
|---|---|---|
| Phase 0-1（0-12 月） | 🟢 极低 | myCad 体量小，不在大厂雷达上 |
| Phase 2（12-24 月） | 🟢 低 | 即使大厂推免费版，针对的是 SolidWorks 用户而非 myCad 用户群 |
| Phase 3（24+ 月） | 🟡 中 | 如果 myCad 在某细分市场取得成功，可能引起注意 |

### 早期信号

- 大厂招聘"CAD 架构师"
- 行业会议出现"大厂 CAD 战略"演讲
- 竞品突然推出针对你目标用户群的功能
- 你的早期商业客户被大厂以"免费迁移"挖走
- 关键开源 CAD 项目获得大厂战略投资

### 缓解措施

#### M6.1 不在"功能广度"赛道竞争
- 大厂的资源能让其在功能数量上永远碾压你
- myCad 永远不要试图"功能比 SolidWorks 更全"
- 专注**架构差异化**（事件溯源、AI 原生、私有化）和**用户群差异化**（隐私敏感、个体设计师）
- **为什么**：差异化是个人/小团队对抗大厂的唯一可能

#### M6.2 私有化部署是天然护城河
- 大厂普遍偏好 SaaS（高利润、易扩展）
- 私有化部署对大厂"不性感"（部署成本高、维护重）
- myCad 在私有化部署上可以做到大厂做不到的"灵活定制 + 透明开源"
- **为什么**：选大厂没有兴趣的市场，活得最久

#### M6.3 开源协议作为护城河
- 大厂自家的 CAD 一定是闭源
- myCad 的 LGPL 内核 + 开放插件生态对企业客户有"反 vendor lock-in"价值
- 即使大厂推出"免费版"，"免费且开源"仍然是不同的价值主张
- **为什么**：开源不仅是协议，更是承诺 — 大厂学不会

#### M6.4 社区生态作为护城河
- 一旦 myCad 有 100+ 第三方插件，迁移成本 = 重写所有插件
- 即使大厂推出竞品，用户不会立刻迁移
- **为什么**：生态是粘性最强的护城河，比技术更难被复制

#### M6.5 持续学习行业动态
- 订阅：Develop3D、CADalyst、Engineering.com
- 关注：r/CAD、r/SolidWorks、r/Fusion360
- 每季度写一份"竞争态势 brief"自存
- **为什么**：早预警 = 早调整，被动挨打最危险

#### M6.6 商业关系的多元化
- 不要让单一企业客户超过年收入 30%
- 持续接触 5-10 家潜在客户而非"All in 1 家"
- 商业插件市场 + 私有化 + 培训认证 收入要分散
- **为什么**：单点依赖 = 单点崩盘

### 大厂"AI CAD" 的特别预案

OpenAI/Anthropic/Google 可能在某天发布"自然语言生成 CAD"颠覆性产品：

#### 预案
- **不要直接对抗** AI 大厂的模型能力
- **做"AI 大厂的下游"**：myCad 实现 AI 模型的"几何执行环境" — 模型生成"画一个法兰"的指令，myCad 真正做参数化建模
- **AI Adapter 设计**：[§四 4.1.8 AI 相关](./04-tech-decisions.md) 的 AI Adapter 就是为此预留的接口
- **结果**：AI 大厂越强，myCad 作为"AI 的几何手"越有价值

### 失败回退方案

如果大厂确实推出有压倒性优势的同类产品：
- **不要立刻关闭项目**：评估是否仍有差异化价值（私有化？某垂直行业？）
- **小众化**：聚焦最坚定的用户群（隐私敏感、特殊需求），接受规模上限
- **被收购可能性**：保持代码质量与社区活跃，未来可能被战略买家收购
- **Pivot**：myCad 的架构组件（事件溯源 CAD 库、约束求解器封装）可独立成产品

## 7.7 风险汇总矩阵

```
影响 →    🟢低             🟡中                      🔴高
概率 ↓
🔴高                                                 [R1] 资源瓶颈
                                                    [R4] 架构漂移*
🟡中                                                 [R2] LGPL 商业化
                          [R5] 生态冷启动 → 重灾区
                                                    [R3] 求解器实现*
🟢低                      [R6] 大厂竞争

* R3 与 R4 实际影响通过缓解措施可降到中等，但若不采取措施则为高
```

**Top 3 必须重点投入缓解资源的风险**：
1. **R1 资源瓶颈** — 时间盒纪律是项目存亡的根基
2. **R5 生态冷启动** — 决定商业模式能否成立
3. **R3 求解器实现** — 决定 MVP 能否交付

**轻松一些的风险**：
- **R2 LGPL** — 设计阶段做对，运行阶段几乎无忧
- **R6 大厂竞争** — 短期不必焦虑，长期看差异化能否守住
- **R4 架构漂移** — 流程纪律到位即可缓解
