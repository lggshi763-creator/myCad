### 1.3 网络环境作战（Day 3-5）— 这周最大的时间黑洞

按 vcpkg 报错的迭代顺序：

| 错误 | 根因 | 解法 |
|---|---|---|
| `CMakeUserPresets.json:2: Invalid extra field "$comment" in root object` | CMake preset schema 不接受 root 的注释字段 | 删 |
| `CMakeUserPresets.json: Duplicate preset` | user file 不允许同名 override root preset | 改名 `local-debug` + `inherits` |
| 多次 `curl error 35 (SSL connect error)` | Windows schannel + GFW + CRL CDN 被墙 → schannel 拉不到 CRL → 拒绝握手 | `--ssl-no-revoke` + 代理 7897 + `tools/vcpkg-rescue.ps1` |
| `Failed to connect to github.com port 443` | git.exe **不读** HTTP_PROXY 环境变量 | `git config --global http.proxy http://127.0.0.1:7897` + 关 `http.lowSpeedLimit/Time` |
| `vcpkg-root path = C:\Program Files\Microsoft Visual Studio\18\Community\VC\vcpkg` | VS 进程无 `VCPKG_ROOT` env，自动 fallback 到 VS 自带 vcpkg | preset 里硬编码 `CMAKE_TOOLCHAIN_FILE` 到 `E:/dev/vcpkg/...` |
| `your current branch 'master' does not have any commits yet`（vcpkg registry cache） | 上次 fetch 中断后 packfile 写盘但 ref 没更新 → unborn 状态 | `rm -rf $LOCALAPPDATA/vcpkg/registries/{git,git-trees}` —— 这个 case **本周复发了 3 次** |
| `Device or resource busy` 删 vcpkg cache | TortoiseGit 的 `TGitCache.exe` 在扫 .git 目录锁文件 | `taskkill /IM TGitCache.exe /F` 后再删 |
| 链接错误 `__std_find_*_pos_*` 找不到 | 机器只装 VS 18 但 preset 写 `Visual Studio 17 2022` → CMake 静默回退 → toolset 选了 14.44 而 vcpkg 选 14.50 → CRT 错位 | preset 显式 pin `"toolset": "host=x64,version=14.50"` + `generator: Visual Studio 18 2026` |
| `qtbase@6.10.2 没有所需的功能 openglwidgets` | docs §8.2.5 那段 vcpkg.json 例子过时（Qt 6.10 已经把 openglwidgets feature 撤了） | 改 `["gui", "widgets", "opengl"]` |
| VS 跑出"Open Folder"模式（`out/build/x64-debug` 而非 `build/local-debug`） | 用户用 `File → Open → Folder` 进入项目，VS 走 legacy CMakeSettings.json 模式而非 preset | 删 `.vs/` 后用 `File → Open → CMake...` 打开 `CMakeLists.txt` |
| `X_VCPKG_ASSET_SOURCES = x-file,...` 报"未知资产提供程序类型" | 我搞混了 binary cache 和 asset cache 的语法（`files,...` 是前者） | 删掉 asset cache 配置 |

## 2. 卡点与教训

### 2.1 反复重发的 vcpkg registry cache 烂状态

**复发 3 次**。每次网络中断 / 锁竞争 / 进程 kill 不干净，`%LOCALAPPDATA%/vcpkg/registries/git` 都进入 "unborn master" 状态——packfile 在但 ref 没更新——下次 vcpkg 启动时所有 port 报"不存在"。

**已沉淀**：[`tools/vcpkg-rescue.ps1`](../../tools/vcpkg-rescue.ps1) 半自动化 + "vcpkg 出错时第一反应清这两个目录"已写进项目共识。

**未沉淀**：还应该把这套清理逻辑也包进一个 `tools/vcpkg-reset-registry-cache.ps1`，避免每次 user 手敲 `Remove-Item`。

### 2.2 VS 18-only 机器的 preset 错位

机器只装了 VS 18（2026），preset 写 `Visual Studio 17 2022`。CMake 找不到 17，**静默 fallback** 到 18，但选 toolset 时不挑最新（选 14.44 而非 14.50）。vcpkg 那边独立挑（vswhere 默认最新 = 14.50）。两边对不上 → 链接缺新 CRT 符号。

**已沉淀**：`CMakeUserPresets.json` 的 `local-debug` preset 显式 pin `toolset: host=x64,version=14.50` + `generator: Visual Studio 18 2026`，本地走这个 preset；`CMakePresets.json` 的 `vs2022-x64-debug` 留给 CI（GitHub windows-2022 runner 装 VS 17）。

**未沉淀**：将来 VS 19 出来 / CI 升级 windows-2025 时，要批量改名 `vs2022-x64-*` → 实际版本，是个**待清理**的语义债。

### 2.3 schannel CRL 死锁是常态化阻塞

Windows + GFW 环境下，**任何 https 站点的 CA CRL CDN 被墙都会握手失败**。本周撞了 python.org / sqlite.org / github.com 多次。

**已沉淀**：知道 `--ssl-no-revoke` 是出口；`tools/vcpkg-rescue.ps1` 自动化喂回。

**未沉淀**：vcpkg 内置 curl 没办法关 CRL 检查，每次都要绕过 vcpkg 自己手动喂——这是体验上的硬伤，等 vcpkg-tool 上游某天加 `--ssl-no-revoke` 透传选项才会真正解决。

### 2.4 tooling 选择层面的"假修复"

DeepSeek 加了 `CMAKE_MSVC_RUNTIME_LIBRARY` 那条 placebo 是教训：**AI 修构建错误时容易"加点东西看着像修过"，而不是定位真因**。今后任何 AI 给的 CMake / 构建系统改动都要问一句"这条改动如果删掉，错误是不是会回来？"——是 → 真修复；不是 → placebo。

## 3. 学到的 / 决定的

| 主题 | 决定 |
|---|---|
| Doxygen 注释样式 | `///` + `@brief` 英文 + 详情中文 + `@throws` / `@thread-safe` 别名（已写进 README） |
| Domain 层零依赖 | `<format>` / `fmt::format` 不可用；用 `std::string` 拼接（强化 ADR-0002） |
| VS 启动方式 | **必须** `File → Open → CMake...`，不能 `Open Folder`（写进 README） |
| vcpkg manifest baseline | 必须等于本地 `$VCPKG_ROOT` 真实 HEAD（每次升级 vcpkg 后要同步） |
| preset 命名 | `vs2022-` 前缀是历史包袱，**保留不改**（避免 CI workflow 同步调整），等需要时再统一重构 |
| 多 toolset 共存 | 长期建议在 VS Installer 卸 14.44，只留最新；目前用 preset pin 兜底 |
